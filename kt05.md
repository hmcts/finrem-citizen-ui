## 1. Document Journey Overview

The upload journey is a multi-step wizard that takes a citizen user from selecting document types through to submitting those documents to CCD (Case Curation Database).

```
Access Code Validation
        ↓
Before You Start → Confidentiality → FDR → Document Type Selection
        ↓
Upload Documents (per type, one file at a time) → CDAM → Session
        ↓
Check Upload → Send to Other Party → LinkDocumentsToCase() → CCD
        ↓
Confirmation + GOV.UK Notify Email
```

Two session keys drive the journey:

| Key | Purpose |
|---|---|
| `req.session.DocumentSelection` | Selected document types + FDR flag |
| `req.session.documents` | Uploaded file metadata pending CCD submission |

## 4. Upload Journey Structure

Steps are defined in `src/main/config/general-upload-config.ts` and orchestrated by `routes/generalUpload/index.ts`.

### Steps in order

| Step | Route | What happens |
|---|---|---|
| `before-you-start` | GET `/upload/before-you-start` | Static guidance page |
| `confidentiality` | GET / POST | User acknowledges data handling |
| `fdr` | GET / POST | Records whether this is an FDR submission |
| `document-type-selection` | GET / POST | User adds/removes document types via autocomplete; stored in `DocumentSelection` |
| `upload-documents` | GET / POST | Files uploaded to CDAM immediately on selection; metadata stored in `documents` session |
| `check-upload` | GET / POST | User reviews files and auto-rename/combining preview |
| `send-to-other-party` | GET / POST | Final confirmation; triggers `LinkDocumentsToCase()` on POST |
| `confirmation` | GET | Success page |

### Session state at each step

```
After document-type-selection:
  req.session.DocumentSelection = {
    documentDetails: [{ id, value: { DocumentType, ... } }],
    isFinancialDisputeResolution: false
  }

After upload-documents:
  req.session.documents = {
    documentDetails: [{ id, value: { DocumentFileName, DocumentLink, ... } }],
    isFinancialDisputeResolution: false
  }

After send-to-other-party (POST):
  req.session.documents → deleted
  req.session.caseData  → reloaded from CCD
```

## 5. Document Type Model

Defined in `src/main/app/case/definition.ts`.

### `CitizenUploadDocumentType` enum (65+ values, selected examples)

```typescript
enum CitizenUploadDocumentType {
  ATTACHMENTS_TO_FORM_E           = "Attachments to Form E",
  BANK_STATEMENTS                 = "Bank statements",
  CHRONOLOGY                      = "Chronology",
  HEARING_BUNDLE                  = "Hearing bundle",
  FINANCIAL_STATEMENT_FORM_E      = "Financial statement: Form E, E1 or E2",
  WITNESS_STATEMENT               = "Witness statement",
  OTHER_DOCUMENT                  = "Other document",
  // ... 60+ additional types
}
```

### `CitizenUploadDocument` interface

```typescript
interface CitizenUploadDocument extends HasCaseDocument {
  DocumentType:     CitizenUploadDocumentType;
  DocumentFileName: string;         // May be auto-renamed
  OriginalFileName?: string;        // Original name before rename
  isFDR:            YesOrNo;
  DocumentLink:     CitizenDocument;
  DocumentDateAdded: DateAsString;
}

interface CitizenDocument {
  document_url:        string;  // e.g. http://cdam.../documents/{cdamId}
  document_binary_url: string;  // e.g. http://cdam.../documents/{cdamId}/binary
  document_filename:   string;
}
```

### `ListValue` wrapper (CCD list format)

```typescript
interface ListValue<T> {
  id: string;   // Locally generated UUID — CCD list item key only
  value: T;
}
```

> **Important:** The `id` on `ListValue` is **not** the CDAM document ID. The CDAM document ID is the last path segment of `DocumentLink.document_url`.

### Auto-rename format map (`src/main/common-constants.ts`)

Document types that trigger auto-rename follow the pattern:

```
{UserName}-{Format}-{DD-MM-YYYY}.{ext}
```

Examples:

| Document type key | Rename format |
|---|---|
| `chronology` | `Chronology` |
| `hearing-bundle` | `bundle` |
| `witness-statement` | `WitnessStatements` |
| `position-statement` | `PositionStatement` |

### Combined PDF format map

Multiple uploads for these types are merged into one PDF on submission. Examples:

| Types | Combined filename |
|---|---|
| `bank-statements`, `payslips`, `p60` | `{UserName}-SupportingFinancialDocuments-{date}.pdf` |
| `attachments-to-form-e` | `{UserName}-AttachmentsFormE-{date}.pdf` |
| `updating-disclosure` | `{UserName}-UpdatingDisclosure-{date}.pdf` |

## 6. Multer Usage & Temporary File Storage

Configured in `src/main/routes/generalUpload/home.ts`.

```typescript
const upload = multer({
  storage: multer.diskStorage({
    destination: tmpdir(),
    filename: (_req, file, callback) => {
      callback(null, `${randomUUID()}${path.extname(file.originalname)}`);
    },
  }),
  limits: {
    fileSize: 100 * 1024 * 1024,  // 100 MB
  },
});
```

| Setting | Value | Reason |
|---|---|---|
| Storage | OS `tmpdir()` (disk) | Avoids buffering large files in memory |
| Filename | `{UUID}.{ext}` | Prevents path traversal and filename collisions |
| File size limit | 100 MB | Enforced by Multer before file is fully written |
| Pre-check | `Content-Length` ≤ 101 MB | Rejects oversized requests before Multer reads the body at all |

Temp files are deleted in a `finally` block after the CDAM upload completes or fails. If the process crashes mid-upload, orphaned temp files may remain in `tmpdir()` and will be cleaned up by the OS on reboot.

---

## 7. File Size Limits & Allowed Extensions

| Setting | Value |
|---|---|
| Maximum file size | 100 MB |
| Allowed extensions | `.jpg`, `.jpeg`, `.png`, `.pdf`, `.docx`, `.xlsx` |

The extension check is a whitelist — any other extension is rejected regardless of MIME type.

## 8. Current Validation Behaviour

Implemented in `src/main/functions/util/uploadValidation.ts`, called after Multer writes the file to disk.

### Validation sequence

1. File present check — at least one file must be attached
2. Empty file check — size must be > 0 bytes
3. Size check — must be ≤ 100 MB
4. Extension check — must be in the allowed list
5. Password protection detection:
   - **PDF:** Scans for `/Encrypt` marker in file content
   - **DOCX / XLSX:** Checks encrypted ZIP flag or compound file format header

### Error messages

| Key | User-facing message |
|---|---|
| `NO_FILE` | You must upload at least one file before continuing |
| `EMPTY` | The selected file is empty |
| `TOO_LARGE` | Your file must be smaller than 100MB |
| `INVALID_TYPE` | Your file must be in jpg, png, pdf, docx, or xlsx format |
| `PASSWORD_PROTECTED` | The selected file is password protected |
| `UPLOAD_FAILED` | The selected file could not be uploaded - try again |

Validation errors are stored in `req.session.uploadErrors[documentType]` and displayed as a GOV.UK error summary on the next render. They are cleared once the page has been re-rendered.

## 9. CDAM / Document Management Integration

**Client:** `src/main/app/document/CaseDocumentManagementClient.ts`

**Base URL:** `config.get('services.caseDocumentManagement.url')`

### Authentication headers (all requests)

```
Authorization:        Bearer {user.accessToken}
ServiceAuthorization: {S2S token from getServiceAuthToken()}
experimental:         true
```

### `create()` — upload a file

- Builds `multipart/form-data` with `caseTypeId`, `jurisdictionId`, `classification`, and file(s)
- `POST /cases/documents`
- Returns `DocumentManagementFile[]` containing:
  - `_links.self.href` — document URL (contains CDAM document ID)
  - `_links.binary.href` — binary download URL
  - `originalDocumentName` — filename as stored in CDAM (may be auto-renamed)

### `getDocument()` — download a file

- `GET /cases/documents/{documentId}/binary`
- Response streamed directly to the browser — no buffering in Node

## 10. How Uploaded Files Are Attached to a Case

After files are uploaded to CDAM and stored in session, `LinkDocumentsToCase()` is called on POST to `send-to-other-party`:

```
req.session.documents.documentDetails
        ↓
Add isFDR flag to each document
        ↓
Determine CCD field key by case role:
  APPLICANT   → citizenApplicantDocument
  RESPONDENT  → citizenRespondentDocument
        ↓
CaseApi.triggerEvent(caseNumber, { citizenApplicantDocument: [...] }, eventName)
  Event: CUI_applicantUploadDocuments | CUI_respondentUploadDocuments
        ↓
CCD persists documents on the case
        ↓
delete req.session.documents
        ↓
Reload caseData into session
        ↓
Send GOV.UK Notify email to user
```

## 11. How Document Metadata Is Persisted

Each uploaded file is stored in session immediately after CDAM upload:

```typescript
{
  id: generateUuid(),             // CCD list item key (not CDAM ID)
  value: {
    DocumentFileName: "JohnSmith-Chronology-17-07-2026.pdf",  // Auto-renamed
    OriginalFileName: "my-chronology.docx",                   // What user chose
    DocumentType:     "Chronology",
    DocumentLink: {
      document_url:        "http://cdam.../documents/{cdamId}",
      document_filename:   "JohnSmith-Chronology-17-07-2026.pdf",
      document_binary_url: "http://cdam.../documents/{cdamId}/binary",
    }
  }
}
```

This structure is sent verbatim to CCD on submission and is not transformed further.

## 12. How Document Download Works

**Route:** `GET /documents/:documentId/download` in `home.ts`

```
Verify req.session.caseNumber === caseId query param
  → 403 Forbidden if mismatch

Get system user token via getSystemUser()

CaseDocumentManagementClient.getDocument(res, documentId)
  GET /cases/documents/{documentId}/binary
  → Stream binary response directly to browser
  → Set Content-Type and Content-Disposition from CDAM response headers
```

No document content is buffered in Node — the response is piped end-to-end from CDAM to the browser.

---

## 13. How Document Removal Works

**Route:** `DELETE /documents/remove/:fileId` in `home.ts`

- Finds the entry in `req.session.documents.documentDetails` by matching `ListValue.id`
- Removes it from the array
- **No CDAM call is made** — the file remains in CDAM but is de-referenced from the session
- Returns JSON `{ count: remaining }` for the client-side UI to update without a full page reload

> **Note:** If the user abandons the journey after removing a file, the original CDAM document is orphaned and not cleaned up.

## 14. Ownership / Authorisation Checks

| Check | Where | Behaviour on failure |
|---|---|---|
| User authenticated | OIDC middleware (all private routes) | Redirect to IDAM login |
| Access code | `enter-access-code.ts` | Error message; no session set |
| Case number match | Download and previously-uploaded-docs routes | 403 Forbidden |
| Case role set | `LinkDocumentsToCase()` | Error thrown |
| Documents exist in session | `LinkDocumentsToCase()` | Error thrown |

The `user.accessToken` (OAuth2 JWT) is passed on every CDAM and CCD API call. The S2S token from `getServiceAuthToken()` authenticates the service itself in backend-to-backend calls.

---

## 15. Applicant / Respondent Visibility

- Case role (`CaseRole.APPLICANT` / `CaseRole.RESPONDENT`) is set at access-code validation and stored in `req.session.user.caseRole`
- On submission, documents go to either `citizenApplicantDocument` or `citizenRespondentDocument` CCD field
- On the previously-uploaded-documents page, the correct collection is fetched based on the user's case role
- There is no cross-role visibility in this UI — each party only sees their own documents

## 16. Error Handling — Failed Uploads

```
Multer error (LIMIT_FILE_SIZE, etc.)
  → Caught by error-handling middleware in home.ts
  → Translated to FILE_VALIDATION_ERRORS.TOO_LARGE or UPLOAD_FAILED
  → Stored in req.session.uploadErrors[documentType]
  → Redirect to returnUrl; error displayed on next render

Validation error (type, size, password)
  → Same session error storage and redirect flow

CDAM error (network / 4xx / 5xx)
  → Propagates as unhandled exception
  → Caught by global error handler
  → Temp file still cleaned up in finally block
```

---

## 17. Error Handling — Failed Download / Removal

**Download:**

| Scenario | Behaviour |
|---|---|
| `caseNumber` mismatch | 403 Forbidden returned immediately |
| No user in session | Error thrown → global error handler |
| CDAM returns 4xx / 5xx | Error propagates → global error handler |

**Removal:**

- Errors in session manipulation propagate to the global error handler
- No network call is made, so there are no CDAM-specific failure modes

**Email notification failure:**

- Caught and logged separately from the CCD submission
- Does **not** block the document submission completing
- AppInsights tracks the failure with `caseNumber`, `email`, and Notify response status

## 18. Required Test Coverage

Before making any changes to document handling, ensure the following are covered:

| Area | What to cover |
|---|---|
| **File validation** | Each error case: no file, empty, too large, wrong type, password-protected PDF, password-protected DOCX/XLSX |
| **Multer config** | Size limit enforcement; temp file cleanup on success and error |
| **CDAM upload** | Happy path; CDAM 4xx / 5xx error handling; FormData construction |
| **PDF conversion** | Conversion success; non-200 throws error; PDF re-uploaded to CDAM; `DocumentFileName` updated to `.pdf` |
| **Session shape** | Documents stored correctly after upload; cleared after submission |
| **`LinkDocumentsToCase`** | Correct CCD event fired; correct field key for applicant vs respondent; `isFDR` set correctly |
| **Download** | Happy path binary streaming; 403 on case number mismatch; CDAM 404 handling |
| **Removal** | Correct item removed by `ListValue.id`; no CDAM call made; JSON response returned |
| **Auto-rename** | Filename format per document type; deduplication counter for multiple uploads of same type |
| **Email notification** | Success sends notification; failure does not block submission |
| **Previously uploaded docs** | Correct collection fetched per case role; 403 on case number mismatch |

## 19. Accessibility Concerns

| Area | Concern |
|---|---|
| File upload inputs | Each `govukFileUpload` must have a visible label and an `aria-describedby` pointing to the hint text |
| Error summary | GOV.UK `govukErrorSummary` component is used — focus is moved to it on page load when errors are present |
| Error messages | Each file input shows an inline `govukErrorMessage` linked by `id` |
| Remove document link | `aria-label="Remove {filename}"` must be set to distinguish multiple remove links on the same page |
| Auto-rename preview | Displayed as a `<p>` with `<strong>` — ensure screen readers can identify the expected filename before upload |
| Combining notice | Shown in `check-upload.njk` as a `<p>` block — must be associated with the relevant document group heading |
| Progress indication | During AJAX file upload, the UI should indicate loading state; ensure this is announced to screen readers |

## 20. Production Support Considerations

| Scenario | What to investigate |
|---|---|
| **Large file rejection** | Check `Content-Length` pre-check log entry; look for Multer `LIMIT_FILE_SIZE` error in server logs |
| **Failed upload (CDAM error)** | Check server logs for CDAM 4xx/5xx response; verify S2S token is not expired |
| **Orphaned temp files** | Check `tmpdir()` on app pods; files should be deleted in `finally` block but can accumulate on crash |
| **Document not visible after upload** | Check `req.session.documents.documentDetails` was populated; check if `LinkDocumentsToCase` was called; check CCD event history for the case |
| **Virus scanning / CDAM rejection** | CDAM handles AV scanning internally; a rejected file returns an error response from CDAM — treat as UPLOAD_FAILED |
| **Email not received** | Check AppInsights for GOV.UK Notify error tracking; verify `DOCUMENT-UPLOAD-EMAIL-TEMPLATE-ID` secret is set |
| **403 on download** | `caseNumber` in session does not match `caseId` in URL — user may have switched cases or session may have expired |
| **Session loss mid-journey** | Session store (Redis in non-local environments) may have evicted the session; user must restart the journey |
